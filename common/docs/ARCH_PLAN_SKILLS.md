# 方案对比：Skill 驱动 vs 本地代码驱动

> 讨论于 2026-10-21。你的想法是：PC 端全部用 WorkBuddy 自动化 + Skill 完成，
> 不装任何代码；服务器只保留「按时读腾讯文档 → 调 QQ API」。
> 本文评估这个想法，结论是**成立**，但有两个前提必须先说清。

---

## 一、先确认哪些已经验证过

| 能力 | 是否可行 | 证据 |
|---|---|---|
| Agent 直接读腾讯文档表格 | ✅ **已实测** | `smartsheet.list_tables / list_fields / list_records` 全部调通 |
| Agent 直接写腾讯文档表格 | ✅ **已实测** | 今天成功改列名（5 列）+ 写入 5 天数据 + 删 9 行空行 |
| 自动化调用 skill | ✅ 支持 | 自动化的 `skills` 字段可指定 `tencent-docs` |
| 读公众号文章 | ⚠️ **未验证，风险最高** | 没有专门的 skill；只有 browser-skill，且它在本机 daemon 起不来 |
| 读食谱图片 | ⚠️ 取决于模型 | 当前模型 `deepseek-v4-flash` 明确不支持读图 |

**腾讯文档这一环已经证明可以完全不写项目代码。** 这是你想法里最扎实的部分。

---

## 二、你的方案 vs 现在的方案

### 现在的（代码驱动）

```
PC（13 个脚本）
  inbox 截图 → extract_menu（调 LLM API）→ validate → 写腾讯文档
  ↓ scp 上传（已废弃，因为腾讯文档是唯一真相）
服务器（13 个脚本，同样一份）
  run_daily → 读腾讯文档 → 发 QQ
```

问题：代码在 PC 和服务器各一份，PC 那侧其实只是「一次性搬运工」，
却要维护 venv、依赖、更新同步。

### 你的（Skill 驱动）

```
PC（0 个脚本）
  WorkBuddy 自动化 + tencent-docs skill
  看食谱图/文章 → 理解 → 直接调 skill 写腾讯文档
  ↓
服务器（4 个文件）
  run_daily.py + doc_client.py + send_qq.py + common.py
  每天 9:50 读腾讯文档 → 发 QQ
```

**净减少**：PC 侧 13 个脚本 → 0；服务器 13 → 4。
而且彻底消灭了「本地留档 JSON」这个中间层（它本来就是冗余的）。

---

## 三、必须先接受的两个前提

### 前提 1：模型必须能看图

你说得对，WorkBuddy 自动化本身跑在模型上。如果那个模型是多模态的：

- 截图丢进某个文件夹 → agent `Read` 图片 → 自己看清行列 → 调 skill 写入
- **完全不需要 LLM_API_KEY**

如果不是多模态（比如现在的 `deepseek-v4-flash`），这条路直接断掉。
**这是硬性前提，不是可选项。**

### 前提 2：读公众号这一环，暂时无解

我查了已装的 skill：

```
browser-skill     ← 能开浏览器，但没有针对公众号的优化
gzh-design        ← 是「公众号排版」，不是「读公众号」
tencent-docs      ← 文档读写，无关
```

**没有专门的「读公众号文章」skill。** 而 browser-skill：

- 本机 daemon 起不来（`os error 5`，Job Object 限制）
- 即使起来，公众号文章页对 IP 很敏感（我实测过机房 IP 必被验证码拦）

**但这不重要** —— 见下一条。

---

## 四、关键洞察：你可能根本不需要读公众号

你学校发的是**图片食谱**。那么：

| 你获取食谱的方式 | 需要读公众号吗 |
|---|---|
| 微信里截图 → 存到某个文件夹 | ❌ 不需要 |
| 直接在 WorkBuddy 对话里粘贴图片 | ❌ 不需要 |
| 让 agent 去爬公众号文章 | ✅ 需要（且不可靠） |

**跳过公众号这一步，整条链路就只剩「看图 → 写表格」两件事，都能用 skill 完成。**

这也顺带解决了 IP 风控问题 —— 截图是你自己的操作，不涉及任何爬取。

---

## 五、真正的代价：失去确定性

这是我要诚实提醒的地方。

现在的 `validate()` 会硬性拦截：日期格式错、日期重复、餐次名不规范、菜名含顿号。
不通过就**中止写入**，绝不会把坏数据写进去。

Agent 驱动的流程没有这层保护。它可能：

- 把「周二」算成周三（日期推算错）
- 漏掉某一餐
- 把两道菜合成一条

**缓解办法**：让 agent 写完立刻 `list_records` 读回来，把读到的内容原样贴进汇报，
你自己扫一眼。人眼校对是最后一道闸 —— 反正一周只有 5 行。

这比代码校验弱，但对这个场景够用。**代价是你得看一眼汇报。**

---

## 六、结论与建议

### 建议采纳你的方案，但保留一个极小的服务器端

```
PC：WorkBuddy 自动化 + tencent-docs skill（零代码）
    每周日 20:00 → 读图 → 写腾讯文档 → 读回来贴进汇报

服务器：4 个文件，装一次就不用再管
    每天 09:50 → 读腾讯文档 → 发 QQ 群
```

### 迁移只需三步

1. **换模型**：在 WorkBuddy 里换成支持视觉的模型
2. **建自动化**：新建一个只依赖 `tencent-docs` skill 的每周任务
   （不用工作区文件、不用 venv）
3. **精简服务器**：删掉 `extract_menu.py / ingest.py / weekly_ingest.py /
   fetch_article.py / menu_store.py / publish_menu.py / save_menu.py`，
   只留 `run_daily.py / doc_client.py / send_qq.py / common.py`

### 什么情况下不该采纳

- 你很在意「每周数据绝对正确、不需要人看」
- 你的模型迟迟换不成多模态
- 学校开始发**文字版**食谱（那还是需要读文章，仍无解）

---

## 七、一个折中选项

如果你不想一次拆干净，可以保留 `save_menu.py` 作为「唯一本地脚本」：

Agent 看完图 → 输出 JSON → 喂给 `save_menu.py` → 校验 + 写入

好处：保留 validate() 的硬校验，坏处：PC 上还得有 Python 和 venv。
考虑到它只需要一个脚本，其实不算负担。你决定。
